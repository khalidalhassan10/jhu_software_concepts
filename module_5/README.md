Grad Café Analytics (Module 5: Software Assurance and Secure SQL)
=================================================================

A Flask service that stores Grad Café admission results in PostgreSQL and shows an analysis
page with two actions: **Pull Data** (fetch new entries from Grad Café) and **Update Analysis**
(re-read the database), plus a search endpoint. Module 5 hardens it: Pylint 10/10, SQL
injection defences with a LIMIT on every query, a least-privilege database user, a dependency
graph, pinned requirements with a `setup.py`, and a Snyk scan.

* **Repository (SSH):** `git@github.com:khalidalhassan10/jhu_software_concepts.git`
* **Module 4 documentation (Read the Docs):** https://jhu-software-concepts-khaled.readthedocs.io/en/latest/

Fresh install
-------------

Requirements: Python 3.12 and PostgreSQL 16 or newer. Run these from `module_5`.

### Option 1: pip

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -r requirements.txt
pip install -e .
```

### Option 2: uv

```bash
python3.12 -m pip install uv
uv venv --python 3.12 .venv
source .venv/bin/activate
uv pip sync requirements.txt
uv pip install -e .
```

`uv pip sync` makes the environment match `requirements.txt` exactly: it installs what is
listed and removes anything that is not, so every machine ends up with identical versions.
`pip install -e .` (or `uv pip install -e .`) installs the project itself from `setup.py` in
editable mode, so `import src...` works from any folder and code changes apply immediately.

To regenerate the pinned file after changing `requirements.in`:

```bash
uv pip compile requirements.in --universal --python-version 3.12 --no-header --no-annotate -o requirements.txt
```

The dependency graph also needs Graphviz, which is not a Python package:
`brew install graphviz` or `conda install -c conda-forge graphviz`.


Database setup
--------------

Create the two databases and the table, as the owner (`postgres`):

```bash
createdb -U postgres gradcafe
createdb -U postgres gradcafe_test
export DATABASE_URL="postgresql://postgres:PASSWORD@localhost:5432/gradcafe"
python -m src.load_data ../module_3/llm_extend_applicant_data.json
```

`load_data` creates the `applicants` table if needed and inserts the records; running it
again inserts nothing new, because rows whose `p_id` already exists are skipped.

Then create the app's least-privilege user and give it a password:

```bash
psql "$DATABASE_URL" -f db/least_privilege.sql
psql "$DATABASE_URL" -c "\password gradcafe_app"
```

`gradcafe_app` is not a superuser and cannot create databases or roles. It may only connect to
`gradcafe`, use the `public` schema, and run `SELECT` and `INSERT` on `applicants`: exactly what
the app does. It cannot `UPDATE`, `DELETE`, `TRUNCATE`, `DROP`, `ALTER` or `CREATE` anything.


Configuration
-------------

No credentials are written in the code. The app reads `DATABASE_URL` if it is set; otherwise it
builds the URL from five variables:

| Variable | Example |
|---|---|
| `DB_HOST` | `localhost` |
| `DB_PORT` | `5432` |
| `DB_NAME` | `gradcafe` |
| `DB_USER` | `gradcafe_app` |
| `DB_PASSWORD` | the password set with `\password` |

Copy `.env.example` to `.env`, put the real values in `.env` (it is listed in `.gitignore`, so
it is never committed), and export it before running the app:

```bash
cp .env.example .env
set -a; source .env; set +a
unset DATABASE_URL
```


Run the application
-------------------

```bash
flask --app src.flask_app:create_app run
```

Open http://127.0.0.1:5000/analysis.

* **Update Analysis** re-reads the database and refreshes the answers.
* **Pull Data** fetches Grad Café entries newer than the database. If Grad Café refuses scripts
  (HTTP 403), pages are read through a Google Chrome window that is already open on
  thegradcafe.com and has passed its verification.
* While a pull runs, both buttons answer `409 {"busy": true}`.
* **Search:** `GET /api/applicants?term=Fall 2026&degree=Masters&sort=gpa&limit=5` returns
  matching applicants as JSON. Filters: `term`, `degree`, `status`, `program`,
  `us_or_international`; `sort` must be one of `p_id`, `date_added`, `gpa`, `gre`, `term`,
  `program`; `limit` is clamped to 1–100 (default 20).

Command-line versions of the analysis: `python -m src.query_data` (raw SQL) and
`python -m src.orm_queries` (SQLAlchemy).


SQL injection defences
----------------------

* Every SQL statement is built with psycopg's composition tools: `sql.SQL` for the fixed text,
  `sql.Identifier` for table and column names, and `%s` placeholders for every value.
* User input never becomes SQL text: filter values are passed as parameters, `%`, `_` and `\`
  typed by the user are escaped so they match only themselves, and the sort column must be on
  an allow-list.
* Every query has a `LIMIT`; user-supplied limits are clamped to 1–100.
* Building a query (`build_search`) is separate from running it (`search_applicants`).
* `tests/test_sql_safety.py` sends classic attacks (`' OR 1=1 --`, `DROP TABLE`, `UNION SELECT`,
  `%`, `_`) through the search and the web endpoint: each returns no rows, and the table is intact.


Run the tests
-------------

From the repository root, with `TEST_DATABASE_URL` set (the tests use the owner account on a
throwaway database whose name must end in `_test`, because they empty the table):

```bash
export TEST_DATABASE_URL="postgresql://postgres:PASSWORD@localhost:5432/gradcafe_test"
pytest module_5/tests -m "web or buttons or analysis or db or integration"
```

This runs all 133 tests and fails unless coverage of `module_5/src` is 100%. The tests never use
the internet: the scraper, loader and query can be replaced with fakes through `create_app(...)`.
